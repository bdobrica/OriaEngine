# Oria / SecondContext adapter contract v1

This consumer contract records the HTTP subset inspected in SecondContext commit
`b7f117f428ac9bebfc8019bb6c63d7a43bde61d4`. It does not introduce an upstream
endpoint or depend on SecondContext's Go implementation types. The local checkout
was read to verify wire behavior; it is not a runtime or test dependency.

## Identity and authentication

The external subject is the canonical lowercase string of the Oria internal user
UUID, sent as top-level `user`. No Telegram identifier is sent. Session identity
is an Oria-generated UUID sent as `metadata.session_id`. The MVP keeps one session
per subject, across separate Telegram conversations. The owning service rejects a
session belonging to another subject.

`Authorization: Bearer <token>` is sent only when configured. The existing upstream
API binds that token to a single authenticated subject: `user` must match it.
**A shared service token does not currently authorize multiple Oria users.** The
adapter never retries an identity conflict under a default subject or drops `user`.
Without auth, subject isolation depends on trusted private service access; the
upstream endpoint must not be exposed to untrusted callers. A delegated service
credential requires an explicit upstream security contract before implementation.

## Conversation

`POST /v1/responses` receives:

- `model: "context-agent-1"`, `stream: false`;
- `user`, `input` containing the application-filtered active message;
- `metadata.session_id`, a static `session_title`, and a bounded goal enum;
- `instructions` containing memory guidance and optional typed natal facts.

Required result fields are `id`, `object: "response"`, `status: "completed"`,
`output_text`, `metadata.session_id`, and
`metadata.context_packet.user_external_id`. Both scope echoes must match the
request. Unknown result fields are ignored for additive compatibility. The
application treats output as an untrusted draft requiring later policy validation.

Facts reuse Astrology MCP v1 `NatalResult`: positions, houses, angles, aspects,
availability/accuracy and engine provenance. No birth input, coordinates, city,
timezone, raw timestamp, identity metadata or generic facts dictionary is accepted.
Facts go into request instructions, not user input or memory ingestion. Upstream
currently does not persist these instructions. It does persist filtered user text,
assistant text and retrieval context; a generated answer can quote chart facts.
“Ephemeral” describes the supplied facts block, not a promise that every derived
fact disappears from the transcript or upstream LLM infrastructure.

## Explicit memory

`POST /memory/ingest` receives `user`, `metadata.session_id`, `source: "oria"`,
`type`, and identical fixed `raw_text` / `summary` phrases. The only application
inputs are the enumerated conversational preferences/prior topics defined in
`oria_engine.context.contracts`. There is no free-text memory API, raw profile
parameter, model-driven memory extraction or arbitrary metadata forwarding.

Result fields `id` and `user_id` are upstream UUIDs, `source` must be `oria`, and
`summary` must match the fixed phrase. Upstream user IDs are not Oria user IDs.
The response API retrieves semantic memory but does not automatically ingest chat
history; the caller explicitly records approved preferences/topics. Selection of
these memories belongs to future active routing, not inferred consent.

## Failures and retries

Requests have a 20-second total deadline, a maximum 3-second connect timeout, and
a 256-KiB decoded response limit. Redirects and ambient proxy settings are disabled.
Connection establishment failures retry up to three attempts, with 0.1/0.2-second
backoff inside the deadline. HTTP errors, malformed/wrong-scope responses, read or
write failures and total deadline expiry produce generic exceptions. Cancellation
propagates. No error bodies, URLs, credentials or private text enter diagnostics.

Response creation and ingestion have no supported idempotency key. Retrying an
ambiguous operation at a higher layer can duplicate downstream messages/memories.
Stage 16 must resolve this before claiming durable exactly-once context effects;
the Stage 11 inbound-event transaction does not cover an external service.

## Subject deletion: required, unavailable upstream

The adapter interface is `purge(user_id: UUID) -> None`. Success means the subject's
sessions, messages, memories, people/topics, beliefs, outcomes, graph/projection
records and vector index data are no longer retrievable. It must be scoped,
repeatable and recoverable after partial downstream failure. Absence of all subject
data may count as success only when the owning service confirms it. New subject
writes must be fenced during deletion by the owning application/service workflow.

The inspected upstream exposes only `DELETE /memory/{memoryID}`, not a subject-wide
purge. That endpoint cannot satisfy this contract. The adapter raises
`PurgeUnsupported` without issuing partial deletes. A missing endpoint, generic
404, timeout or index failure must never be interpreted as completed deletion.
No route/status schema is invented here: a versioned upstream purge contract and
implementation remain required. Stage 18 cannot be marked complete on this basis.
