# Oria / SecondContext adapter contract v1

This consumer contract records the response/memory HTTP subset inspected in
SecondContext commit `b7f117f428ac9bebfc8019bb6c63d7a43bde61d4`, plus its additive
service-auth/purge extension in commit `4bb8dba86e7f91cb49db6b9c6aad311d03b57099`.
The owning contract is `docs/contracts/service-context-v1.md` with ADR 0001 in
SecondContext. The adapter does not depend on its Go implementation types; the
sibling checkout is not an Oria runtime or test dependency.

## Identity and authentication

The legacy external subject is the canonical lowercase Oria internal user UUID,
sent as top-level `user`. No Telegram identifier is sent. Session identity is an
Oria-generated UUID in `metadata.session_id`, reused across conversations. Foreign
session ownership is rejected by the owning service.

`Authorization: Bearer <token>` is sent when configured. With an empty
`SECOND_CONTEXT_SUBJECT_NAMESPACE`, existing ordinary subject-bound tokens retain
their original semantics. Conflicting body selectors never fall back to a default
subject. Legacy unauthenticated development requests still work but cannot purge.

With the explicit setting `SECOND_CONTEXT_SUBJECT_NAMESPACE=oria`, the subject is
`oria:<UUID>`. The adapter sends that value in both `user` and the per-request
`X-SecondContext-Subject` header. SecondContext's separate
`AUTH_SERVICE_TOKENS=oria:=<secret>` credential authorizes only canonical UUIDs in
that namespace and only response creation, memory ingestion and subject purge.
It requires `AUTH_ENABLED=true`. Existing ordinary tokens never gain delegation.
Keep namespace and session identity configuration stable; switching them is not a
data migration. SecondContext and Oria remain separate database owners.

## Conversation

`POST /v1/responses` receives:

- `model: "context-agent-1"`, `stream: false`;
- `user`, `input` containing the application-filtered active message;
- `metadata.session_id`, a static `session_title`, and a bounded goal enum;
- `instructions` containing memory guidance and optional typed natal/transit facts.

Required result fields are `id`, `object: "response"`, `status: "completed"`,
`output_text`, `metadata.session_id`, and
`metadata.context_packet.user_external_id`. Both scope echoes must match the
request. Unknown result fields are ignored for additive compatibility. The
application treats output as an untrusted draft requiring later policy validation.

Facts reuse Astrology MCP v1 `NatalResult` and additive `TransitResult`: positions,
available natal houses/angles, aspects, availability/accuracy and engine provenance.
Transit facts carry the target calculation timestamp. No birth input, coordinates,
city, timezone, birth timestamp, identity metadata or generic facts dictionary is accepted.
Facts go into request instructions, not user input or memory ingestion. Upstream
currently does not persist these instructions. It does persist filtered user text,
assistant text and retrieval context; a generated answer can quote chart facts.
“Ephemeral” describes the supplied facts block, not a promise that every derived
fact disappears from the transcript or upstream LLM infrastructure.

## Explicit memory

`POST /memory/ingest` receives `user`, `metadata.session_id`, `source: "oria"`,
`type`, and identical fixed `raw_text` / `summary` phrases. The only application
inputs are the enumerated conversational preferences/prior topics defined in
`oria_engine.context.contracts`. There is no free-text memory API, raw profile
parameter, model-driven memory extraction or arbitrary metadata forwarding.

Result fields `id` and `user_id` are upstream UUIDs, `source` must be `oria`, and
`summary` must match the fixed phrase. Upstream user IDs are not Oria user IDs.
The response API retrieves semantic memory but does not automatically ingest chat
history; the caller explicitly records approved preferences/topics. Selection of
these memories belongs to future active routing, not inferred consent.

## Failures and retries

Requests have a 20-second total deadline, a maximum 3-second connect timeout, and
a 256-KiB decoded response limit. Redirects and ambient proxy settings are disabled.
Connection establishment failures retry up to three attempts, with 0.1/0.2-second
backoff inside the deadline. HTTP errors, malformed/wrong-scope responses, read or
write failures and total deadline expiry produce generic exceptions. Cancellation
propagates. No error bodies, URLs, credentials or private text enter diagnostics.

Response creation and ingestion have no supported idempotency key. Retrying an
ambiguous operation at a higher layer can duplicate downstream messages/memories.
Stage 16 must resolve this before claiming durable exactly-once context effects;
the Stage 11 inbound-event transaction does not cover an external service.

## Subject deletion

`purge(user_id: UUID) -> None` issues `POST /v1/subjects/purge` with
`{"user":"<resolved external subject>"}`. It uses the same bearer and, in namespace
mode, subject header as other adapter calls. Only an HTTP success whose JSON has
`contract_version: 1`, `status: "completed"` and the exact requested `user` counts
as completion. Unknown additive response fields are ignored. Generic/missing
responses, wrong subjects, unsupported routes, failed indexes and timeouts raise
`ContextUnavailable`; they must not be treated as completed deletion.

SecondContext fences the authenticated subject, writes a durable deletion marker,
removes all vectors for its canonical user ID in the configured Qdrant collection,
and deletes canonical user content with cascades. Sessions, messages, memories,
entities, people, topics, person/topic models, beliefs, graph edges and outcomes
are covered. A minimal subject identifier/timestamp marker remains and rejects
late authenticated requests with 410. Repeated purge, including an absent subject,
returns the same scoped completion semantics without recreating user data.

A failure leaves the marker and permits retrying the same subject after recovery;
the existing adapter connection retries remain bounded, and the deletion orchestrator
owns later retries after ambiguous responses. New registration must use a new Oria
UUID. Stage 18 owns user confirmation and Oria-side cleanup. Backups, retired index
collections and upstream provider retention are outside this HTTP purge operation.
