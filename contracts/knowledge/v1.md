# Knowledge and context projections — candidate v1

Status: candidate schemas and Oria-side consumer requirements. **Not a published
SecondContext capability.** No knowledge HTTP calls or remote ingestion are enabled.
Canonical DTOs are used in [Oria local encrypted memory](../../docs/private-memory.md);
the proposed projection lifecycle remains a candidate.
[ADR 0002](../../docs/adr/0002-private-life-events-and-context-projections.md)
records ownership. [Python definitions](../../src/oria_engine/knowledge/contracts.py)
are the source for [generated JSON schemas](v1.json); regenerate with
`uv run python scripts/generate_knowledge_schema.py` and check with `--check`.

## Canonical records

Canonical `EntityRecord`/`EventRecord` payloads stay in Oria's encrypted storage.
No model-selectable owner field exists. The authenticated application owner UUID
scopes repositories and all referenced records; structural schema validation alone
cannot establish ownership. Entity kinds cover people, pets, organizations,
possessions and other user-defined entities, without requiring separate accounts.
Events have stable UUIDs, monotonically increasing revisions, a user-described
type, participants/roles and an owner-scoped source operation UUID derived from
trusted provider/update identifiers. Own-birth events reference a natal-profile
UUID/revision, using that profile UUID as their virtual source rather than
creating a second editable birth profile.

`TemporalEvidence` retains the original expression, persisted UTC reference clock,
explicit/current-preference/unknown timezone provenance, resolution-rule version,
optional anchor revision and optional resolved value. Date-only, UTC instant,
local clock with unknown offset, partial date, interval and anniversary are tagged
distinctly. Unknown date/time remains absent. No noon/midnight is invented for an
event. Calendar validation rejects impossible partial dates, reversed or mixed
precision intervals, naive UTC instants and inappropriate recurrence anchors.
The runtime resolver will validate IANA timezone rules, anchor ownership and clock
ambiguity; a DTO is not a temporal resolver. Storage years need not match the
astrology engine's narrower supported calculation years.

## Context projection

`ContextProjection` admits only a stable record reference/revision, bounded label
and summary, user-statement versus interpretation classification, source record
references, house-topic tags 1–12 and optional salience with basis/method version.
There is no arbitrary metadata, raw profile, coordinates or birth-date field.
Free text must still be prepared/checked by the application: typed labels and
summaries do not themselves prove the absence of birth values or credentials.
Raw birth inputs must not be smuggled into summary/label text. Calculation facts
continue through existing typed fact contracts, not remembered narrative claims.
House-topic tags describe relevance, not calculated placements.

## Proposed HTTP lifecycle

The following routes and schemas are a proposal for the owning service. Its current
[service-context v1](../second-context/v1.md) authorizes only response creation,
fixed memory ingestion and subject purge. Oria must not call candidate routes or
assume that existing service tokens authorize them. SecondContext must add an
explicit scoped allowlist and acceptance/implementation evidence first; no direct
SQL/Qdrant access or alternate unscoped memory-ingest route is permitted.

All proposed operations use the existing bearer authentication and selected-subject
header; the body `user` must match that subject. Responses echo the exact subject.
Keep existing v1 response/memory/purge clients and semantics unchanged. These
knowledge payloads have their own `contract_version: 1` and bounded operation tags.
A future revision must be published explicitly; unknown fields are rejected by the
candidate closed schemas rather than silently becoming raw-data escape hatches.

| Proposed endpoint | Request | Success |
| --- | --- | --- |
| `POST /v1/knowledge/upsert` | `ProjectionUpsert`: subject, operation UUID, projection | `ProjectionReceipt`, operation `upsert`, exact record/revision, coverage `projection_and_indexes` |
| `POST /v1/knowledge/query` | `ProjectionQuery`: subject, record references and/or house themes, limit 1–20 | `ProjectionMatches`: exact subject and bounded matches |
| `POST /v1/knowledge/delete` | `ProjectionDelete`: subject, operation UUID, record reference at deletion revision | `ProjectionReceipt`, operation `delete`, exact record/revision, coverage `active_stores_and_linked_history` |

Success is HTTP 200 with the typed completed receipt/results. Validate scope,
operation UUID/type and record UUID/kind/revision using `validate_receipt`; verify
subject and requested result limit with `validate_matches`. Rehydrate matches
against current Oria owner/revision/deletion state before use. Structural validators
do not authorize a record or prove that the service actually erased anything.
Unknown routes, missing capabilities, malformed/wrong-subject responses and generic
2xx bodies are failures, never evidence of support or completed deletion. Do not
silently downgrade selective deletion to index hiding or whole-account erasure.

## Ordering, retries and erasure

A `(subject, operation_id)` identifies one immutable operation/body. An identical
retry returns the same completion; reuse with different content is HTTP 409.
Within `(subject, record kind, record UUID)`, an upsert must advance revision or
repeat an identical already-committed revision. Stale or same-revision conflicting
writes return 409. Atomic canonical/index completion or durable recovery is owned
by SecondContext, not an Oria cross-database transaction.

Deletion uses a revision greater than every prior revision of the canonical record.
It writes a durable per-record fence before erasing projections and dependent
summaries, vectors, graph links and retained conversation/draft references derived
from it. Completion means all declared active-store/history coverage is erased.
Do not retain old payloads in idempotency history; retain only minimal operation
and revision/fence metadata needed to reject late writes. A deleted record UUID
cannot be resurrected by a higher-revision upsert; a new intentional record gets
a new UUID. Lost/ambiguous acknowledgements retry the same operation. A pending
subject purge prevents every late projection mutation. Dependency failures return
503 and keep fences durable, never a completed receipt.

Canonical corrections advance revision, invalidate derived readings and enqueue
replacement projections. Query never returns deleted records or obsolete revisions;
Oria additionally checks dependencies before use. A correction does not silently
rewrite a human transcript. If the product promises selective erasure, linked
retained history must be erased through the owning service. Ordinary independent
mentions and source provenance need an explicit tested linkage/coverage policy;
a service cannot advertise history erasure by deleting one vector.

Oria owns the durable projection work queue and local suppression during retries.
The service owns remote transactional/index behavior and any minimal record fences.
Existing full-subject purge must include projection content, indexes, operations
and record fences under its minimal subject fence. Backup/retired-index/provider
retention limits remain explicitly outside active-store erasure, as in v1.

No deployment should infer support from generic health checks. Before ingestion,
require an identified compatible owning-service release plus real service contract
tests for authentication, isolation, duplicate/conflicting operations, revision
ordering, linked-history erasure, crash recovery, selective deletion and subject
purge. Oria's DTO/acknowledgement tests are consumer checks, not that evidence.
